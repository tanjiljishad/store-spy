# Environment Variables Reference

Evergreen reference — update this file whenever a new environment variable is
introduced. See `docs/milestone-8-subphase-a-production-architecture-research.md`
Section 13 for the original audit that found `SCHEDULER_SECRET` undocumented
(now fixed by this file's existence) and `.env.example` / `.env.test.example`
for copy-paste templates.

**Never commit a real secret value.** `.env` and `.env.test` are gitignored;
`.env.example` and `.env.test.example` are committed templates and must only
ever contain placeholders.

| Variable | Required? | Classification | Used by | Notes |
|---|---|---|---|---|
| `DATABASE_URL` | Always | SECRET | Prisma client, everywhere | Postgres connection string. Different value per environment — local/staging/production must never share a database. |
| `AUTH_SECRET` | Always | SECRET | Auth.js (JWT signing), read implicitly by `next-auth` — not referenced directly as `process.env.AUTH_SECRET` in application code | Generate with `openssl rand -base64 32`. Unique per environment — a shared value across environments would let a staging-issued session token authenticate in production. |
| `AUTH_TRUST_HOST` | **Required in staging/production** on any non-Vercel host; not needed locally | Not a secret (`"true"`) | Auth.js core (`@auth/core`'s `setEnvDefaults`), read implicitly, not referenced directly in application code | Auth.js only auto-trusts the incoming request's `Host` header when `NODE_ENV !== "production"` (true for local `next dev`) or when `AUTH_URL`/`VERCEL`/`CF_PAGES` is set. On Render (or Fly.io, or any self-hosted platform) running `next start` with `NODE_ENV=production`, none of those apply, so every Auth.js endpoint (`/api/auth/session`, `/csrf`, `/providers`, sign-in callbacks) fails closed with `UntrustedHost` — reproduced directly in Milestone 8 Sub-phase C by running a real `next start` locally. Set to `"true"`. See https://errors.authjs.dev#untrustedhost. |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Optional | ID: server-only / Secret: SECRET | `src/lib/auth/auth.ts` | App runs fine without them — the Google sign-in button simply doesn't render (`configuredProviders.google`). Real values need a real Google OAuth app with production-domain callback URLs registered (Section 15 of the Sub-phase A research doc). |
| `FACEBOOK_CLIENT_ID` / `FACEBOOK_CLIENT_SECRET` | Optional | Same split as Google | `src/lib/auth/auth.ts` | Same optionality as Google. |
| `SERPAPI_API_KEY` | Optional locally, required for marketing collection | SECRET | `src/lib/marketing/source-factory.ts` | Without it, `getConfiguredMarketingSource()` throws — the marketing scheduler tick and `npm run marketing-scheduler:tick` fail loudly rather than silently no-op-ing. Every other feature (Shopify crawling, growth signals, dashboard) works completely unaffected. Real, billed key — see SerpApi's plan tiers before setting a production value; there is no pay-as-you-go, only monthly commitments (Sub-phase A research, Section 12). |
| `SCHEDULER_SECRET` | Optional locally, **required in staging/production** | SECRET | `src/app/api/internal/scheduler/tick/route.ts`, `src/app/api/internal/scheduler/marketing-tick/route.ts` | **What it protects**: both routes trigger a real scheduler tick — real outbound Shopify crawls and, for the marketing route, real billed SerpApi calls. Both fail CLOSED (HTTP 503) if this variable is unset, so an unauthenticated deployment refuses every request rather than silently accepting one. A request must send this exact value in the `x-scheduler-secret` header to succeed. **Which endpoint uses it**: both `/api/internal/scheduler/tick` and `/api/internal/scheduler/marketing-tick`, same value for both. **How the worker relates to it**: the worker process (`scripts/worker.ts`, Milestone 8 Sub-phase B) calls `runSchedulerTick()`/`runMarketingSchedulerTick()` *directly*, in-process — it does **not** go through these HTTP routes at all, so the worker itself needs no `SCHEDULER_SECRET`. These routes remain useful as a manual-trigger/health-check surface for a human operator (or an external monitoring check) to invoke a tick on demand, independent of the worker's own cadence. **Is it required in staging?** Yes, if staging's worker (or a human) will ever hit these HTTP routes — set a real (staging-only) value. Not required if staging exclusively relies on the worker process's direct, in-process ticking and the HTTP routes are never actually called. **How to generate a value**: `openssl rand -base64 32`, same as `AUTH_SECRET`. |
| `NODE_ENV` | Platform-managed | Not a secret | `src/lib/db/prisma.ts` (dev-mode Prisma-client singleton caching) | Set automatically by `next build`/`next start`/most hosts — not something a developer sets by hand locally (`next dev` sets it to `development` itself). |
| `TRUSTED_PROXY_HOPS` | Optional, defaults to `1` | Not a secret | `src/lib/security/rate-limit.ts` (`getClientIp()`) | **What it protects**: every rate limit in the app (signup, login, `/api/analyze`, store sub-routes) is keyed on the caller's IP, extracted from `x-forwarded-for`. That header is a comma-separated list the *client* fully controls except for what real proxies between it and this process append — trusting the first entry (or `x-real-ip`) lets an attacker mint an unlimited number of fresh buckets by prepending a fake IP. `getClientIp()` instead counts `TRUSTED_PROXY_HOPS` entries in from the **right**, which only a real proxy hop can have appended. Default `1` matches Render's topology (`render.yaml`): exactly one reverse proxy in front of the web service. `0` means "no proxy at all" — `x-forwarded-for` is ignored entirely and every such request shares one `"unknown"` bucket, since this framework's Route Handlers expose no raw socket address to fall back to (`NextRequest.ip` was removed upstream in Next 15). Only change this if the deployment topology changes (e.g. a CDN is added in front of Render, making it 2). |
| `TURNSTILE_SECRET_KEY` | Optional locally, **required in staging/production** | SECRET | `src/lib/security/turnstile.ts` (`verifyTurnstileToken()`) | **What it protects**: Milestone 12's anonymous analysis form (`POST /api/analyze` without a session) — the server-side half of the Cloudflare Turnstile challenge. Fails CLOSED if unset, same convention as `SCHEDULER_SECRET`: every anonymous request is rejected (`turnstile_failed`) rather than silently skipping verification. Get a real value from the Cloudflare dashboard (Turnstile product), paired with `NEXT_PUBLIC_TURNSTILE_SITE_KEY` below — same site, two different keys. |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | Optional locally, **required in staging/production** | Not a secret (site keys are public by design — embedded in the page) | `src/components/analysis/TurnstileWidget.tsx` | The client half of the same challenge as `TURNSTILE_SECRET_KEY` above — must be from the *same* Cloudflare Turnstile site. Unset locally, the widget doesn't render at all and shows an explanatory message instead of a broken challenge; the server-side check still fails closed regardless, so this being unset never means verification is skipped, only that anonymous analysis is unusable until it's set. `NEXT_PUBLIC_`-prefixed per Next.js convention — inlined into the client bundle at build time. |
| `ANONYMOUS_CRAWL_HOURLY_CEILING` | Optional, defaults to `500` | Not a secret | `src/app/api/analyze/route.ts`, `src/lib/entitlements/anonymous-analysis.ts` | Milestone 12 §1.3's global circuit breaker: the total count of anonymous shallow probes started across ALL IPs in the last hour. Above this, anonymous analysis returns `503` regardless of any individual IP's own quota — the backstop for distributed abuse (many IPs, few requests each) that the per-IP 3/24h quota alone can't see. Authenticated analysis is never affected. |
| `UNSUBSCRIBE_TOKEN_SECRET` | Optional locally, **required in staging/production** | SECRET | `src/lib/marketing/unsubscribe-token.ts` (`GET /unsubscribe`) | **What it protects**: Milestone 12 §4.1's no-login unsubscribe link — an HMAC-SHA256 of the user's id, so the link itself proves who it's for without a session. Fails CLOSED the same way `TURNSTILE_SECRET_KEY`/`SCHEDULER_SECRET` do: unset means every unsubscribe link is rejected as invalid, never silently trusted unverified. A dedicated secret, never `AUTH_SECRET` reused — a leaked unsubscribe link (these are meant to be emailed, and email is not a secure channel) must never also be able to forge a session. **Generate with**: `openssl rand -base64 32`, same as `AUTH_SECRET`. |
| `EMAIL_VERIFICATION_TOKEN_SECRET` | Optional locally, **required in staging/production** | SECRET | `src/lib/auth/email-verification-token.ts` (`GET /verify-email`) | **What it protects**: the no-login email-confirmation link — an HMAC-SHA256 of `userId:email`, so the link proves who it's for and stops verifying if the account's email ever changes (unlike `UNSUBSCRIBE_TOKEN_SECRET`'s id-only binding, which has no email-change feature to worry about). Fails CLOSED the same way `UNSUBSCRIBE_TOKEN_SECRET` does. A dedicated secret, never `AUTH_SECRET` or `UNSUBSCRIBE_TOKEN_SECRET` reused. **Generate with**: `openssl rand -base64 32`. |
| `RESEND_API_KEY` | Optional locally, **required in staging/production** | SECRET | `src/lib/email/resend-client.ts` | **What it protects**: the Resend API key used to actually send email. Without it (or without `EMAIL_FROM`), `sendEmail()` throws — the signup route and the resend-verification route both catch that (non-fatal for signup, a `502` for an explicit resend request), so a missing/misconfigured key degrades to "no email sent," never a crash. Get a real value from https://resend.com/api-keys. |
| `EMAIL_FROM` | Optional locally, **required in staging/production** | Not a secret — a From address is visible in every email header regardless | `src/lib/email/resend-client.ts` | The sender address for every outbound email. Locally, Resend's shared sandbox sender `onboarding@resend.dev` works with no domain setup but can only deliver to the email on your own Resend account. A real deployment needs a verified sending domain (Resend dashboard) and a real address on it — an unverified From domain gets every send rejected by Resend, the same fail-loud-not-silent posture as everything else on this page. |
| `NEXT_PUBLIC_META_PIXEL_ENABLED` / `NEXT_PUBLIC_META_PIXEL_ID` | Optional, off by default | Not a secret — a Pixel ID is exactly as public as every real Meta Pixel already is | `src/lib/marketing/pixels/meta.ts`, `src/components/marketing/pixels/MetaPixel.tsx` | Milestone 12 §4.2 Step 2: the base Meta Pixel (page-view/retargeting only, never a conversion event). BOTH must be set — the flag is a genuine, independent kill switch, not just "ID present = on." Client-side only, inlined at build time; never read server-side. Loads only on `/`, `/terms`, `/privacy` (never `/dashboard`, `/admin`, `/login`, `/signup`), and only after the visitor's `bw-cookie-consent` cookie reads `"granted"`. |
| `META_CONVERSIONS_API_ACCESS_TOKEN` | Not yet usable — Milestone 12 §4.3 (the credential vault) hasn't shipped | SECRET (once it exists) | `src/lib/marketing/pixels/meta.ts` (`isMetaConversionsApiConfigured()`, `dispatchMetaConversionEvent()`) | **What it's for**: the server-side half of Meta's conversion tracking — the signup event, dispatched from the worker via `MarketingConversionEvent`, never the request path. **Current state**: `isMetaConversionsApiConfigured()` reads this var and is expected to return `false` — this is the documented PROVIDER SEAM, mirroring `billing/checkout.ts`'s own precedent. Setting it locally makes dispatch attempts throw a clear "not implemented yet" error into the row (`FAILED`, not a crash) rather than silently pretending to work, since there is no real vendor call behind it yet. Do not configure a real value until §4.3 provides a real credential-storage mechanism (encryption at rest, audit-on-decrypt) — this variable, sitting in plain `.env`, is not that mechanism. |
| `NEXT_PUBLIC_GA4_MEASUREMENT_ENABLED` / `NEXT_PUBLIC_GA4_MEASUREMENT_ID` | Optional, off by default | Not a secret — a GA4 measurement ID is exactly as public as every real GA4 tag already is | `src/lib/marketing/pixels/google.ts`, `src/components/marketing/pixels/GooglePixel.tsx` | Milestone 12 §4.2 Step 2, vendor 2: the GA4 base tag (page_view/session telemetry only, never a conversion event). Configured with ONLY this GA4 measurement ID, deliberately — never a Google Ads `AW-` id; see `google.ts`'s own file comment for why that keeps `googleads.g.doubleclick.net` out of the CSP entirely. Client-side only, inlined at build time; never read server-side (`GOOGLE_MEASUREMENT_PROTOCOL_API_SECRET` below is a separate server-only variable, even though its dispatch reuses *this* ID). Loads only on `/`, `/terms`, `/privacy`, and only after `bw-cookie-consent` reads `"granted"`. |
| `GOOGLE_MEASUREMENT_PROTOCOL_API_SECRET` | Not yet usable — Milestone 12 §4.3 (the credential vault) hasn't shipped | SECRET (once it exists) | `src/lib/marketing/pixels/google.ts` (`isGoogleMeasurementProtocolConfigured()`, `dispatchGoogleConversionEvent()`) | **What it's for**: the server-side half of Google's conversion tracking — the signup event, dispatched from the worker via `MarketingConversionEvent`, never the request path, using GA4's Measurement Protocol (not the separate Google Ads API) targeted at the same property as `NEXT_PUBLIC_GA4_MEASUREMENT_ID` above. ## Never shared between environments

`AUTH_SECRET`, `DATABASE_URL`, OAuth client credentials (production OAuth apps
need production callback URLs — a shared credential would either break
staging or misconfigure production), `SERPAPI_API_KEY` (a shared key means
local/staging experimentation consumes real, billed production quota),
`SCHEDULER_SECRET`, `TURNSTILE_SECRET_KEY` / `NEXT_PUBLIC_TURNSTILE_SITE_KEY`
(a shared Turnstile site would let a bypass or a lowered-friction setting in
one environment affect the challenge served in another), `UNSUBSCRIBE_TOKEN_SECRET`
(a shared value would let an unsubscribe link minted — or forged — in one
environment verify in another), `EMAIL_VERIFICATION_TOKEN_SECRET` (same
reasoning, for confirmation links), `RESEND_API_KEY` (a shared key means
staging test signups consume the same send quota/reputation as real
production email), `META_CONVERSIONS_API_ACCESS_TOKEN`,
`GOOGLE_MEASUREMENT_PROTOCOL_API_SECRET`, `TIKTOK_EVENTS_API_ACCESS_TOKEN`,
`LINKEDIN_CONVERSIONS_API_ACCESS_TOKEN`, and `X_CONVERSIONS_API_ACCESS_TOKEN`
once any is a real value (a shared token would let a staging conversion
event report against the production ad account, corrupting real attribution
data). `NEXT_PUBLIC_META_PIXEL_ID`, `NEXT_PUBLIC_GA4_MEASUREMENT_ID`,
`NEXT_PUBLIC_TIKTOK_PIXEL_ID`, `NEXT_PUBLIC_LINKEDIN_PARTNER_ID`, and
`X_PIXEL_ID` are the exceptions worth calling out explicitly: sharing any
between staging and production would just mix staging traffic into the real
ad account's/property's audience/attribution data — not a security issue,
but a real data-quality one, so use a separate test Pixel/property (or
leave it unset) in staging regardless.

|---|---|---|---|
